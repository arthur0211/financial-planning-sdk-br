# ADR 0008 — matriz instalada, offline e fail-closed

**Estado:** aceito para o harness local; R7 fecha também a admissão do TAR bruto do backend, matriz ainda não autoritativa
**Data:** 2026-08-11

## Contexto

O smoke anterior comparava payload runtime em source, wheel direto e wheel reconstruído do sdist, mas não provava a instalação do mesmo freeze em todos os runtimes declarados nem aplicava uma fronteira externa de rede e filesystem. `requires-python = ">=3.11"` inclui Python 3.14; portanto limitar o metadata para esconder uma célula não observada seria mudança de contrato, não evidência de portabilidade. A matriz fechada permanece Windows/Linux × Python 3.11–3.14.

As opções offline do pip controlam resolução, dependências e cache, mas não constituem uma sandbox. Da mesma forma, um audit hook Python observa chamadas modeladas, mas roda dentro do processo candidato e não substitui uma boundary do host. Build acquisition e execução offline também são fases diferentes: obter previamente Python, a imagem base e wheels da toolchain pode exigir rede; somente build, reconstrução, instalação e rotas do produto sob isolamento contam para a célula.

O modo isolado `-I` não pode provar variação de `PYTHONHASHSEED`, porque implica `-E` e ignora todas as variáveis `PYTHON*` ([documentação do Python 3.14](https://docs.python.org/3.14/using/cmdline.html#cmdoption-I)). Por isso origem de import e determinismo usam processos separados.

## Decisão

Cada célula executada precisa produzir `finplanbr.installed-portability-cell.v1` e satisfazer, sem skip ou xfail:

1. ligar-se ao manifesto integral `finplanbr.source-freeze.v1`, invocado somente por um interpreter já isolado com `-I`, copiar somente suas entradas e repetir hash/tamanho antes e depois da execução;
2. chamar separadamente `python -m build --wheel` e `python -m build --sdist`, conforme as superfícies distintas do [frontend PyPA build](https://build.pypa.io/en/stable/reference/cli.html), fechar o output do backend em um sdist gzip/USTAR canônico, reconstruir um wheel a partir desse sdist e canonicalizar separadamente os dois wheels antes de inspecionar ou instalar;
3. instalar o wheel direto e o wheel reconstruído em venvs descartáveis fora do checkout, com `--no-index --no-deps --no-cache-dir --no-compile`, mantendo zero dependência base de runtime; os flags seguem a superfície documentada do [pip install](https://pip.pypa.io/en/stable/cli/pip_install/), mas a ausência de rede é provada separadamente;
4. observar três superfícies — source, wheel direto e wheel do sdist — em dois contextos: baseline (`PYTHONHASHSEED=0`, locale C, TZ UTC0, Decimal default) e hostil (`PYTHONHASHSEED=4294967295`, locale alternativo, TZ GMT+12, precisão/expoentes/rounding Decimal hostis). Esses processos usam `-P -s` e ambiente sanitizado, para que a seed realmente chegue ao runtime;
5. usar processos `-I` separados somente para provar que os imports vêm do source congelado ou do `site-packages` da venv esperada;
6. exigir bytes e return codes idênticos no SDK, module CLI e console script instalado para validate/compute válido e inválido, JSON malformado, Reference Pack e versão; fechar ainda os quatro schemas e o roster público de reason codes;
7. demonstrar um alvo gravável antes de ativar a boundary, falha de escrita depois dela, fingerprint idêntico das árvores protegidas e precontrol de rede conectado antes de postcontrol bloqueado;
8. exigir o roster fechado corrente de 18 membros do package, 24 membros em cada wheel e 29 arquivos + quatro diretórios no sdist, incluindo a licença Apache-2.0 source-bound conforme o ADR 0012; rejeitar qualquer canary, segredo, arquivo, diretório ou metadata adicional;
9. ligar `README.md` e `pyproject.toml` do sdist byte a byte ao source congelado; o `pyproject` tem roster semântico fechado de build/project/setuptools e o `METADATA` inteiro precisa ser exatamente os headers esperados — incluindo os únicos `Provides-Extra`/`Requires-Dist` — seguidos pelos bytes do README;
10. provar conteúdo de package idêntico entre source, wheel direto, sdist e wheel reconstruído, conteúdo lógico idêntico entre os dois wheels e bytes integrais idênticos entre os dois wheels canônicos. Line endings de metadata gerada podem variar nos artifacts brutos do backend, mas os canonicalizadores validam a equivalência contra a política fechada e substituem somente os membros gerados por uma única representação LF/source-derived. Nenhum arquivo authored do package, packs, LICENSE, README ou pyproject entra nessa normalização;
11. registrar digests raw dos artifacts — incluindo um único `wheel_archive_sha256` comum aos dois wheels e um `sdist_archive_sha256` ligado ao input de rebuild —, digests de inventário/conteúdo lógico, plataforma, microversão Python, toolchain, mecanismo de isolamento, controles e limites não autoritativos.

O sdist bruto emitido pelo setuptools usa PAX para mtimes. Antes de qualquer reconstrução, o canonicalizador lê um snapshot regular `nlink=1`, exige um único membro gzip com `FNAME` exato e sem cauda, aceita no TAR somente um record PAX canônico `mtime` imediatamente associado a cada entrada, confere o roster completo e recusa outros atributos/canais. Os dois `PKG-INFO`, `setup.cfg` e cinco outros membros `egg-info` são normalizados uma única vez na fronteira de entrada e substituídos por LF/source-derived; os authored permanecem byte-exact. O writer `finplanbr-sdist-gzip-ustar-stored-canonical.v1` serializa diretamente o roster USTAR: diretórios e arquivos em ordem normativa, name integral com prefix vazio, campos octais zero-padded/NUL, checksum de seis dígitos + NUL + espaço, `mtime=0`, uid/gid 0, owners/devices vazios, modos 0644/0755, padding de membro zero, dois blocos EOF e padding ao record exato de 10.240 bytes. Em seguida escreve diretamente um membro RFC 1952 com header `1f8b08000000000000ff`, DEFLATE `STORED` em blocos normativos de 65.535 bytes e trailer CRC32/ISIZE. Nenhum byte TAR é delegado ao writer de `tarfile` e nenhum byte comprimido a zlib/zlib-ng. O inspector conserva os parsers raw e `tarfile` reconciliados, mas também reserializa os payloads decodificados e exige igualdade integral do TAR e do gzip; metadata gerada no sdist já canônico precisa ser exatamente LF, sem segunda normalização. Ordem alternativa, número de blocos EOF, spacing octal, codificação de checksum e divisão equivalente entre name/prefix não satisfazem o perfil.

A admissão anterior ao writer também é fechada, não uma normalização genérica de TAR. Cada membro lógico precisa estar na ordem observada do setuptools e ser precedido por exatamente um pseudoheader PAX `mtime`; o campo USTAR `mtime` precisa ser o `round(float(mtime))` que o `tarfile` gravou. O parser exige `name` integral/prefix vazio, slash de diretório, type `0`/`5`, octal zero-padded com NUL, checksum de seis dígitos + NUL + espaço, magic/version exatos, owners/link/devices/reserved vazios, padding zero e EOF no record de 10.240 bytes. Os únicos tuples de atributos admitidos são ligados à célula: Windows usa diretórios 0777, arquivos 0666 e uid/gid 0; Linux oficial usa diretórios 0755, arquivos 0644 e uid/gid 65532. Base-256, byte não zero depois de NUL, owner nominal, profile misto ou de outro sistema, PAX ausente/empilhado, mtime não ligado, ordem alternativa e outra representação equivalente falham antes da canonicalização. A visão estruturada raw é reconciliada campo a campo com `tarfile`; nenhum desses bytes é apagado silenciosamente.

Cada wheel bruto também passa primeiro pelo parser ZIP32 raw e pela visão reconciliada de `zipfile`, com roster, tipos, modes, tamanhos, CRC32 e `RECORD` semanticamente válidos. O canonicalizador `finplanbr-wheel-zip32-stored-canonical.v2` não reutiliza o compressor/backend: valida metadata gerada contra `finplanbr-setuptools-80.10.2-metadata.v2`, deriva `METADATA` dos headers fechados mais os bytes exatos do README congelado, fixa em LF também `WHEEL`, `entry_points.txt` e `top_level.txt`, e serializa diretamente um ZIP32 gap-free com os 23 membros na ordem normativa, nomes ASCII com flags zero, timestamp DOS exato `1980-01-01 00:00:00`, método `STORED`, `version-needed=20`, creator Unix/version 20, `internal_attr=0`, regular file 0644, e zero extra/comment/disk/data descriptor/ZIP64. `RECORD` é regenerado em LF, na mesma ordem, com a self-row única por último. O inspector refaz esses bytes e exige também igualdade exata dos quatro membros gerados; portanto newline, timestamp, ordem, UTF-8 flag alternativo para nome ASCII, versão/creator/mode permitidos pelo parser genérico, `STORED` versus `DEFLATE`, blocos DEFLATE alternativos e ordem das linhas de `RECORD` não sobrevivem como canais. ZIP comment/member comment/extra/prefix/gap, symlink/special attrs, PAX residual, link/special TAR e segundo membro/byte trailing continuam falhando antes ou depois da canonicalização, conforme a fronteira correspondente.

No Linux, o launcher usa containers próprios nomeados/rotulados por nonce, sem porta publicada. As quatro imagens oficiais Python estão fixadas por digest de manifesto em `portability_runtime_pins.py`; a tag móvel não entra na célula. O precontrol roda com rede normal; a célula usa `--network none`, que mantém somente loopback conforme a [documentação do driver none](https://docs.docker.com/engine/network/drivers/none/), mais root filesystem `--read-only`, bind do checkout read-only, usuário não root, capabilities removidas, `no-new-privileges` e tmpfs explícitos. O contexto de build é vazio. Cleanup reconcilia o inventário por label com os nomes conhecidos e, depois que o build foi tentado, também remove a tag derivada integralmente do nonce; assim falha do `image inspect` ou do inventário não deixa a imagem criada sem target de cleanup.

No Windows, o launcher exige sessão elevada. Ele fotografa a ausência dos nomes únicos, cria em `ActiveStore` regras outbound Block apenas para cinco executáveis absolutos dentro da célula, prova bloqueio no Python base e nas duas venvs e remove exatamente essas regras em `finally`. O filesystem usa cópia descartável sob `%TEMP%\finplanbr-portability-windows-<nonce>`, snapshots SDDL e ACE Deny somente nas quatro árvores de teste; o checkout não recebe ACL. A restauração de todos os SDDL e a ausência das regras são pré-condições do `status=passed`. Sem privilégio, controle ativo ou cleanup provado, a célula é `not_observed`/FAIL; não há fallback por audit hook.

Os paths reservados são `/source` read-only, `/work` e `/tmp` descartáveis no Linux; e a raiz temporária por nonce no Windows. Evidência final deve ficar fora do checkout. `dist/` continua ausente e nenhum artefato de build é persistido ou autorizado.

O agregador aceita exatamente oito JSON regulares, sem duplicata ou célula extra, todos no mesmo digest/roster de freeze. Além do digest de paridade único, as oito células precisam carregar o objeto exato `finplanbr.portability-package-binding.v2`, com os três inventários canônicos, os três digests lógicos e os mesmos `wheel_archive_sha256` e `sdist_archive_sha256`. Dentro de cada célula, os hashes raw de direct-wheel, sdist-wheel e do binding de wheel precisam ser iguais; o hash do artifact sdist precisa coincidir com seu binding e com o input capturado antes do rebuild. Oito pares artifact/binding autoconsistentes mas distintos entre si falham `PACKAGING_MATRIX`. Campo ausente, hash raw divergente dentro ou entre células, canary com roster aumentado, célula `not_observed`, controle inativo, cleanup não provado, seed não observada, skip/xfail ou freeze divergente quebra `all_cells_consistent`.

Essas condições provam somente consistência de reports self-issued. O crítico reproduziu oito JSON perfeitos a partir da fixture, sem executar célula, e o agregador R1 devolveu RC0. Como este corte não possui receipt/attestation autenticável fora do checkout, R2 emite sempre `EVIDENCE_ORIGIN_UNAUTHENTICATED`, `evidence_authentication=not_implemented`, `status=failed` e RC1, mesmo quando `all_cells_consistent=true`. O workflow `installed-portability.yml` fixa actions por SHA e agrega artifacts, mas runner/YAML/artifact não autenticado continuam declaração, não prova. RC0 só pode existir em decisão futura que integre receipt externo verificável sem delegar a autoridade ao candidato.

## Consequências

O R1 observado localmente cobriu as quatro células Linux 3.11–3.14, mas foi invalidado como freeze de fechamento: a crítica mostrou que oito digests de paridade distintos, um `unexpected_payload.py` embarcado e oito reports sem execução podiam passar. R2 fechou esses ataques estruturais e tornou explícita a origem não autenticada. A crítica seguinte mostrou que o binding lógico ainda aceitava mudar todos os timestamps DOS sem alterar payload decodificado nem `RECORD`; ordem de membros, método/codificação comprimida, flag de nome e ordem de `RECORD` eram canais equivalentes. R3 canonicalizou o envelope ZIP, mas uma crítica fresca construiu o mesmo freeze `af7d6568…` no Windows e observou 203 CRLF em `METADATA`: o wheel canônico Windows tinha SHA `b8b34dc4…`, contra `598a31b7…` nas quatro células Linux, embora os digests lógicos e a instalação passassem. R4 fechou o wheel. A crítica R5 encontrou sdists gzip diferentes para o mesmo TAR por zlib versus zlib-ng e demonstrou que oito hashes raw distintos não quebravam o agregador. R5 fechou gzip e binding, mas a crítica do freeze `f370…` produziu TARs semanticamente equivalentes e byte-distintos por ordem, EOF, octal, checksum e name/prefix; CRLF e LF final em metadata gerada também sobreviviam porque o inspector normalizava novamente. R6 fechou o artifact final com serializer e reserialização integrais, mas a crítica do freeze `a034…` mostrou que a entrada bruta ainda apagava base-256, tails pós-NUL e owner/group não modelados. R7 fecha essa admissão raw com os dois perfis de backend observados e reconciliação integral. O golden sdist R5 permanece byte a byte, portanto o identificador v1 não muda. Isso permanece evidência candidata até matriz no freeze final e crítica fresca.

Uma execução oficial temporária das oito células no freeze `7b05a078…e9eba` confirmou as quatro células Linux com wheel `598a31b7…`, sdist `fde397d5…` e paridade `635b266f…`; as quatro células Windows retornaram RC1 `windows_firewall_control_requires_elevated_runner`. O agregador falhou como desenhado por `CELL_STATUS` e origem não autenticada. Mudanças posteriores no supervisor invalidam esse freeze como handoff corrente, sem apagar a evidência histórica. O host Windows atual é não elevado e suas quatro células permanecem `not_observed`; mesmo um futuro conjunto técnico 8/8 continuará FAIL até integrar receipt externo. A criação local de Python 3.14 e a inicialização do Docker Desktop são preparação do host, não células.

Os identificadores `R3`/`R5` nomeiam políticas de serialização, não um hash eterno diante de mudança em bytes authored. No source posterior ao freeze `7b05…`, o README empacotado mudou; dois builds descartáveis independentes convergiram ao wheel `5deb64351e9fba573edf8c349cc9e8b923d6a6323bac83d4bfa8b5ebb3707966` e ao sdist `f6ff4ac9a620a932ddabdc0a1078473495807c5aa50750ceab936f08b199e53d`, com direct/rebuilt wheel byte-idênticos e convergência pelos caminhos CRLF/zlib/manual-USTAR. Naquele checkpoint, esses eram os goldens correntes, enquanto `598a31…`/`fde397…` continuavam evidência histórica do source anterior. Nenhum dos pares é autenticação, approval ou release authority.

Na preparação documental anterior para o primeiro push ao GitHub, README e metadata empacotados mudaram novamente. A política então corrente `finplanbr-setuptools-80.10.2-metadata.v3` fechou também URLs, keywords e classifiers; ela superou a menção v2 no parágrafo histórico acima. Depois de remover a data manual do README e registrar a contagem daquela revisão, os caminhos direct/rebuilt, CRLF, alternate-zlib e manual-USTAR convergiram ao wheel `a8b3a74049419b69da171d3441986cb9c9a7f83e843d5f629aa043ca044803fa` e ao sdist `af6b2e3339f0af934b42f38aa5405c2d90bc3e9e0e662ab9a16e2ed258f7f15c`. Esses valores agora são históricos e não são reclassificados como release.

Em 30 de agosto de 2026, o [ADR 0011](0011-secure-build-backend-baseline.md) substituiu o backend vulnerável por `setuptools==84.0.0` e promoveu a política para `finplanbr-setuptools-84.0.0-metadata.v4`. No source então corrente, os caminhos direct/rebuilt locais convergiram ao wheel canônico `9bb574f672d62e15215575a46e4c45865fbf221b40811ef9e7b627efb0bef9cb` e ao sdist canônico `7a0f6d77b9e60a30b9d6d92b777f7f99da9776134241643aa292224a97ba0c27`. O [ADR 0012](0012-apache-source-publication-governance.md) substitui esses goldens pela metadata v5 e pelos rosters com licença. Todos esses hashes continuam candidatos: ainda exigem matriz Windows/Linux no mesmo freeze e não possuem autenticação, authority ou autorização de release.

O controle de filesystem sustenta somente ausência de escrita implícita nas rotas testadas. `--output` é escrita explícita e continua permitido fora das árvores protegidas. Docker/ACL/firewall reduzem a superfície relevante, mas não estabelecem sandbox contra administrador, kernel comprometido, atacante same-UID, processo arbitrário no mesmo interpreter ou supply-chain authority.

Nada nesta decisão altera matemática, schema financeiro, packs v1/v2, authority, F0, licença, publicação ou release.

## Alternativas rejeitadas

- reduzir `requires-python` para evitar Python 3.14;
- tratar `pip --no-index` ou ausência de imports de rede como prova suficiente de isolamento;
- usar apenas audit hook Python como sandbox;
- executar a matriz de seeds sob `-I`, que suprimiria a própria variável testada;
- marcar célula indisponível como skip/xfail ou promover workflow não executado;
- mudar ACL do checkout, criar firewall amplo/persistente ou reutilizar containers não relacionados;
- persistir `dist`, publicar artifact ou inferir authority a partir da matriz.
- aceitar somente igualdade de payload decodificado/digest lógico enquanto headers, ordem e codificação ZIP permanecem livres;
- escolher um compressor DEFLATE “determinístico” como formato canônico, pois manteria uma superfície de codificação desnecessária quando `STORED` é suficiente para este roster pequeno.
- continuar usando `zlib.compress(..., wbits=31)` para o sdist, porque implementações zlib/zlib-ng podem produzir streams válidos diferentes sobre o mesmo USTAR.
- delegar o TAR canônico a `tarfile` ou aceitar equivalência apenas pela visão semântica, pois ordem, field encodings, divisão name/prefix e quantidade de padding/EOF continuam canais raw.
- normalizar novamente metadata gerada durante a inspeção do sdist já canônico, porque isso aceitaria bytes finais fora da representação LF escolhida.
- normalizar todos os membros textuais do wheel, porque isso esconderia drift em código, schemas ou outros bytes authored; somente metadata gerada e fechada pode ser reserializada.
